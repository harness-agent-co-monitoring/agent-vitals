# Vitals raw-data schema

This document describes the files produced by Meta-Harness replay. The primary
objects are:

- one row per prompt token in `attn_tokens.parquet`
- one row per generated token in `tokens-*.parquet`
- a sparse prompt-and-generation attention row for each forced token in
  `attn_sparse.parquet`

The replay teacher-forces a logged trajectory through a reference copy of the
worker model. The generated tokens are fixed to the logged run, so replay does
not sample a replacement trajectory. The attention values describe how the
reference copy reads that trajectory. They may differ from the deployed
instance when weights, quantization, tokenizer, template, or inference
implementation differ.

These files contain raw measurements. The standalone loader does not compute
read lift, consult measures, rankings, or judgments.

## Load the data without a model

`proposer_kit/vitals_data.py` reads the store with pandas and pyarrow. It does
not require the worker model or a GPU.

```python
from vitals_data import (
    iter_attention,
    list_episodes,
    list_stores,
    load_attention,
    load_generation,
    load_manifest,
)
```

The loader provides:

| Function | Result |
|---|---|
| `list_stores(replay_root)` | Candidate-and-dataset store names under a replay root |
| `list_episodes(store_dir)` | Replayed episode IDs in one store |
| `load_attention(store_dir, episode_id)` | Prompt-token attention table |
| `load_generation(store_dir, episode_id)` | Generated-token tables combined into one DataFrame |
| `load_manifest(store_dir, episode_id)` | Integration metadata from `manifest.json` |
| `iter_attention(store_dir)` | `(episode_id, attention_df)` pairs for one store |

One candidate and dataset normally have this layout:

```text
<replay-root>/
└── <candidate>--<dataset>/
    ├── vitals_digest.md
    ├── vitals_digest.parquet
    ├── vitals_delta.parquet
    └── store/
        └── ep-.../
            ├── manifest.json
            ├── messages.jsonl
            ├── regions.jsonl
            ├── tokens-00000.parquet
            ├── attn_received.jsonl
            ├── attn_tokens.parquet
            └── attn_sparse.parquet
```

Not every file is present in every store. Capture options, replay date, and
integration type determine which optional channels are available.

## `attn_tokens.parquet`

This is the primary prompt-side table. `load_attention(store, episode_id)`
returns one row per prompt token.

| Column | Meaning |
|---|---|
| `turn` | Zero-based turn index. Classification episodes normally contain only turn `0`. |
| `idx` | Token position in the rendered prompt for this turn |
| `token_id` | Model vocabulary ID |
| `token_str` | Decoded token piece, so analysis does not need a tokenizer |
| `region_id` | Most specific region containing the token. Declared or parsed sections use `span:<name>`. |
| `attn` | Mean attention received by this prompt position from the turn's forced generated tokens, averaged over captured heads and layers |

The `attn` values for one turn sum to the mean fraction of attention that
lands on the prompt. They do not necessarily sum to `1.0`, because generated
tokens may also attend to earlier generated tokens. Normalize by the total
prompt-side mass before comparing a section with its share of prompt length.

The table supports token-level questions, such as whether the worker reads a
label line but skips the body of the corresponding memory block. Region names
come from the harness declaration when available and from structural parsing
otherwise.

## `tokens-*.parquet`

`load_generation(store, episode_id)` combines these files. The main rows have
`region_id == "gen"` and describe tokens generated by the worker.

| Column | Meaning |
|---|---|
| `episode_id` | Episode identifier |
| `turn` | Zero-based turn index |
| `step` | Generated-token position within the turn |
| `token_id` | Model vocabulary ID |
| `ent` | Entropy of the next-token distribution, in nats |
| `m2` | Probability margin between the two highest-probability tokens |
| `js` | Jensen-Shannon divergence from the preceding step's distribution, in nats. The first step is `0.0`. |
| `fork` | Whether entropy exceeds the configured running-percentile threshold after warmup |
| `kl_ref` | Optional KL divergence from a separate reference condition, in nats |
| `surprisal` | Optional negative log-probability of the emitted token |
| `top_ids`, `top_lp` | Optional top-k token IDs and their log-probabilities |
| `region_id` | `gen` for generated-token rows; prompt scoring can produce other region IDs |
| `attn_share` | Optional attention shares pooled over the regions in `regions.jsonl`, followed by a generated-token bucket |
| `probes` | Additional named scalar probes |
| `t_ms` | Decode time recorded for the step |

Optional logit fields are null when their capture channel was disabled.

`attn_share` preserves a value for each replay-time region. Use
`regions.jsonl` from the same turn to interpret the vector order. The final
value is the share assigned to earlier generated tokens.

## `attn_sparse.parquet`

This table retains the joint between generated steps and the positions they
read. Each row corresponds to one forced generated token.

| Column | Meaning |
|---|---|
| `turn` | Zero-based turn index |
| `step` | Generated-token position, matching `tokens-*.parquet` |
| `pos`, `w` | Top prompt positions and their attention weights. `pos` uses the `attn_tokens.idx` axis. |
| `prompt_mass` | Total attention mass assigned to prompt positions |
| `gen_mass` | Total attention mass assigned to earlier generated positions |
| `gpos`, `gw` | Top earlier generated positions and their attention weights. `gpos` uses the generated-token `step` axis. |

The default replay keeps the top 64 prompt positions and up to 256 generated
positions per forced token. `prompt_mass` and `gen_mass` retain the complete
mass totals, including positions outside those sparse lists.

`pos` and `w` let an analyst recompute uncertainty-conditioned reading after
changing section boundaries. For a section, sum `w` for positions inside its
token range. The result can undercount by at most the omitted prompt-side
tail.

`gpos` and `gw` support reasoning-to-answer analysis. Join an answer token's
generated-side positions to the corresponding reasoning-token rows, then
inspect which prompt positions those reasoning tokens read.

Stores from older replays may lack this file, or carry the prompt-side fields
without `gpos` and `gw`.

## `section_diagnostics.parquet`

Attention replay with `section_diagnostics=True` also writes
`section_diagnostics.parquet`. It contains exact pooled and per-step section
peaks under both averaging conventions and section-attention-weighted
Jensen–Shannon divergence in bits across output steps. Version 2 adds the
focus fields; version 1 remains readable with focus marked `not_captured`.
Older sparse rows cannot generally
recover these values. See the [section diagnostics guide](../../../docs/section_diagnostics.md)
for the fields, missing-data rules, and optional report interface.

The attention-focus JS in this file is not the `js` field in token rows, which
compares successive next-token distributions. Neither contains section
perturbation results. The separate `vitals sensitivity` command writes output
JS in nats to its own JSON file. See the
[output sensitivity guide](../../../docs/output_sensitivity.md) for inputs,
result fields, and controls.

## `manifest.json`

The manifest records the stable episode configuration:

- schema and library versions
- engine, model, and optional reference-model information
- sampler and random seed
- enabled capture channels
- harness-template hash
- creation time
- integration-specific metadata under `meta`

`load_manifest()` returns the `meta` object rather than the complete manifest.
Common Meta-Harness fields include:

| Field | Meaning |
|---|---|
| `task` | Task or example identifier |
| `memory` | Candidate harness name |
| `reward` | Outcome, commonly `1.0` for correct and `0.0` for incorrect |
| `prediction`, `target` | Model prediction and reference target |
| `prompt_sections` | Classification section declaration |
| `prompt_sections_requests` | Resolved multi-turn span requests |
| `call_idx`, `n_calls` | Position and count for multi-call classification designs |
| `n_reasoning_toks` | Number of captured reasoning tokens |
| `think_mode` | How reasoning was represented during replay |
| `provider` | Provider that served the original call |

Classification episode IDs end in `-c<k>`, where `k` is the worker-call
index. The final call is the one that produced the answer.

`think_mode` has three values:

- `reasoning` means replay includes captured reasoning followed by the
  `</think>` seam and final content.
- `nothink` means the provider returned no reasoning block and replay uses the
  recorded no-think seam.
- `legacy` means the older store contains final content only.

When `think_mode` is `reasoning`, the first `n_reasoning_toks` generated rows
belong to the reasoning span. The original reasoning text remains in
`val.json` under `prediction.llm_calls[k].reasoning`.

## Other episode files

### `messages.jsonl`

Each row stores the messages rendered for one turn and, when applicable, the
OpenAI tool schemas. Replay needs this file to reconstruct the prompt.
Messages may contain sensitive user and tool data.

### `regions.jsonl`

Each row stores the ordered regions and token ranges for one turn. This file
maps `attn_share` entries to message regions and `span:<name>` sections.

### `attn_received.jsonl`

Each row stores the received-attention vector for one turn. It is the compact
JSON counterpart of the `attn` column in `attn_tokens.parquet`.

## `vitals_delta.parquet`

The digest writes this file beside `vitals_digest.parquet` when it can pair a
candidate with a parent. Each row describes one prompt-diff hunk from a paired
example.

| Column | Meaning |
|---|---|
| `child`, `parent` | Candidate and parent names |
| `example` | Paired example identifier |
| `class` | `retained`, `removed`, or `added` |
| `side` | Prompt being measured: `parent` or `child` |
| `section`, `family` | Declared section and pooled section family |
| `n` | Number of tokens in the hunk |
| `pos` | Center of the hunk as a fraction of prompt length |
| `mass` | Attention mass received by the hunk |
| `lift` | Digest-convention lift |
| `rel` | Hunk lift divided by the mean lift of its own prompt. `1.0` is average for that prompt. |
| `twin` | Diff-operation index used to pair retained parent and child rows |

The `Delta vs parent` section in `vitals_digest.md` pools this table by hunk
class and section and includes paired outcomes.

## Interpretation rules

- Treat attention as evidence about what the reference model read, not proof
  that a token caused the output.
- Compare raw attention shares within a prompt. Normalize before comparing
  sections across prompts with different lengths.
- The first four context positions can contain attention-sink mass unrelated
  to their text. Exclude them from content-level aggregates.
- Compare candidates on matched examples. In-loop runs use the same fixed
  validation examples across candidates.
- Check the manifest before combining stores. Differences in model, template,
  tokenizer, precision, or schema can invalidate a direct comparison.
